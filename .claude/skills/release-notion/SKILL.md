# 배포 기록을 노션에 남기기

노션에 쓰는 일은 전부 `tool/notion_release_note.dart` 한 스크립트가 한다. 에이전트가 할 일은
**어느 빌드를, 어떤 요약으로** 올릴지 정하는 것뿐이다. 노션 MCP를 직접 부르지 말 것 —
스크립트가 중복 방지(같은 빌드 두 줄 금지)·작업자(커밋 author)·커밋 목록·비교 링크를 다 챙긴다.

## 언제 무엇을

| 상황 | 할 일 |
| --- | --- |
| CI가 배포하면 | 아무것도. `android-distribute.yml`이 태그 직후 자동으로 한 줄 남긴다(요약 작성 = 자동, 본문 = 커밋 제목). |
| "이번 배포 정리해줘" | 그 줄에 **요약을 덧쓴다** (`--update --by Claude` 또는 `--by Codex`). |
| 노션에 없는 옛 배포 | `--build N`으로 만든다. `dist/N` 태그가 있어야 한다. |

## 절차

1. 대상 빌드를 정한다. 말이 없으면 최신 배포다:
   ```sh
   git fetch --tags
   git tag -l 'dist/*' --sort=-version:refname | head -3
   ```
   `dist/N`의 N이 `--build` 값이다. 이전 태그는 스크립트가 알아서 찾는다.
2. 그 범위의 커밋을 **본문까지** 읽는다. 제목만 보고 쓰지 말 것 — 이 저장소의 커밋 본문은
   왜 바꿨는지를 사용자 말 그대로 인용해 두었고, 그게 요약의 재료다.
   ```sh
   git log --no-merges dist/M..dist/N
   ```
3. 요약을 쓴다. 규칙:
   - **사용자가 느끼는 변화**로 쓴다. "함께 방에서 뒤로가기를 누르면 목록으로 접히고 방은 유지돼요"
     (O) / "PopScope를 _minimizeRoom으로 바꿈" (X).
   - 3~8줄, 한 줄에 하나, 한국어, 존댓말 없이 평서문. 큰 것부터.
   - 팀원이 확인해야 할 것(시크릿 추가, 설정 변경, 알려진 한계)은 마지막에 "확인 필요:"로 시작하는 줄.
   - 배포 안 된 커밋을 섞지 말 것 — 범위는 `dist/M..dist/N`이다.
4. 스크립트를 부른다. 요약은 파일로 넘긴다(따옴표·줄바꿈 문제를 피한다):
   ```sh
   dart run tool/notion_release_note.dart --build N --notes-file /tmp/notes.md --by Claude --update
   ```
   Codex면 `--by Codex`. 출력에 노션 URL이 나온다 — 그 URL을 사용자에게 준다.
5. 이미 줄이 있는데 `--update`를 빼면 "이미 기록돼 있습니다"로 끝난다. 그건 정상이다.

## 전제

- 토큰: `.env.notion-mcp`(저장소 루트, git 무시됨)에 `NOTION_TOKEN=…`. Codex의 노션 MCP와 같은 파일이라
  둘 중 하나가 되면 둘 다 된다. 없으면 `.env.notion-mcp.example`을 복사하라고 안내한다.
- 노션 통합 "MCP"가 `셋플로우` 페이지에 연결돼 있어야 한다(데이터베이스가 그 아래다).
- DB id는 `tool/notion-release.json`. 바꾸지 말 것.

## 하지 말 것

- 배포 안 된 커밋으로 줄을 만들지 말 것. 태그가 없으면 스크립트가 거부한다 — 우회하지 말 것.
- `--by 자동`으로 사람 요약을 올리지 말 것. 누가 썼는지는 읽는 사람이 신뢰 수준을 정하는 기준이다.
- 노션 MCP로 같은 DB에 직접 페이지를 만들지 말 것. 중복과 형식 불일치의 원인이 된다.
